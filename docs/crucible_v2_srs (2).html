Crucible as a research operating system.

Crucible v2 replaces the Codex-specific runtime with LangChain Deep Agents Deploy, keeps Postgres as the durable hypothesis DAG, adds a Neo4j-powered domain context engine, and preserves pluggable GPU execution backends for reproducible autonomous research programs.

Summary

Crucible is a research OS above the agent runtime. Deep Agents handles deployment, subagents, sandbox configuration, and model routing. Crucible owns the research-program state machine: hypothesis DAG, evaluator, context broker, evidence graph, replay, budgets, and human-governed execution.

Core principle: the agent session is not the research state. Agent invocations are disposable workers. The durable truth lives in Postgres, Neo4j, object storage, and replayable execution metadata.

Goals and scope

Goals

  • Reproduce the autoresearch reliability primitive on a modern open deployment stack.
  • Store the hypothesis DAG as durable data, not agent-thread history.
  • Add a Critic subagent on an independent model provider.
  • Expose a real trust layer with DAG view, evidence graph, traces, replay, and approvals.
  • Keep GPU execution pluggable across Local, Modal, and Colab.

Non-goals

  • No "fully autonomous scientist" claim in v2.
  • No bio, chemistry, or quant domain packs yet.
  • No multi-tenant SaaS or hosted product in v2.
  • No six-agent swarm until two-agent reliability is proven.
  • No custom inline Python tools in the agent layer.

System architecture

Crucible v2 is split into four durable planes: the product plane (web UI), the orchestration plane (FastAPI state machine), the reasoning plane (Deep Agents deployment with proposer and critic subagents), and the execution plane (GPU-capable backends). Context is handled through a hybrid memory layer: Postgres for operational truth and Neo4j for domain relationships.

UI → Orchestrator → Deep Agents / MCP Tools → GPU Backends
          ↘ Postgres / Neo4j / Object Store / Redis ↙
ConcernPrimary storeReason
Hypothesis DAG, runs, approvals, budgetsPostgresTransactional and queryable
Domain entities, methods, contradictionsNeo4jGraph-native traversal for reasoning context
Artifacts, diffs, logs, snapshotsMinIO / S3Large immutable outputs stay out of DB
Live tracesRedis Streams → DBReal-time streaming then persistence

Deep Agents runtime

Deep Agents replaces the Codex-specific control plane with a model-agnostic deployment runtime. Crucible uses a root agent package, a Proposer subagent, and a Critic subagent. Each subagent has its own deepagents.toml, AGENTS.md, and optional skills.

Proposer

  • Generates one minimal patch for one hypothesis.
  • Consumes compact summary + domain context pack.
  • Returns a structured patch proposal.

Critic

  • Runs on a different model family by default.
  • Checks gaming, leakage, regressions, contradictions.
  • Returns a structured critic verdict.
[agent]
name = "crucible-orchestrator"
model = "openai:gpt-5"

[sandbox]
provider = "modal"
scope = "thread"
image = "python:3.12"

The agent layer is disposable. Every propose or critique action is a short-lived task invocation, not long-lived persistent conversational state.

Context engine

Crucible v2 introduces a hybrid context engine. Postgres stores operational memory and compact summaries; Neo4j stores the domain graph. A Context Broker ingests papers, extracted claims, methods, contradictions, and empirical run outputs into the graph and produces compact domain packs for the agents.

Neo4jPapers, methods, entities, claims, contradictions, hypothesis seeds

Execution model

Crucible separates agent sandboxing from GPU experiment execution. The Deep Agents sandbox is for agent-side code tools and bounded shell/file operations. Crucible backends are for long-running training, evaluation, and simulation jobs.

LayerToolingUse case
Agent sandboxDeep Agents sandbox providersGit, file I/O, tiny scripts, bounded code tools
Execution backendLocal / Modal / ColabTraining, replay, benchmark evaluation, long GPU jobs
Important: these two layers are complementary. The agent sandbox does not replace the experiment backend.

Functional requirements

Research programs

  • Programs are declared in research.yaml with goals, datasets, budgets, metrics, beam width, backend constraints, and papers to ingest.
  • crucible import program.md converts an autoresearch-style spec into the new structure.

Hypothesis DAG

  • Each proposal becomes a durable hypothesis node with parent, depth, status, compact summary, patch diff reference, and Neo4j context reference.
  • Nodes are never deleted; rejected and quarantined paths remain inspectable.

Evaluator

  • Decision states are keep, reject, quarantine, and escalate.
  • Scoring includes primary metric, secondary metrics, cost, reproducibility, novelty, and domain confidence.

Approval and governance

  • Expensive or risky runs create approval requests with TTL and audit trail.
  • Interrupts map to HITL-capable runtime endpoints.

Data model

Postgres remains the operational source of truth. Neo4j augments, but does not replace, relational state.

programs(id, name, version, spec_yaml, neo4j_graph_id, created_at, owner)
hypotheses(id, program_id, parent_id, depth, status, patch_diff_ref, compact_summary,
           proposer_task_id, neo4j_context_ref, created_at)
runs(id, hypothesis_id, backend, started_at, ended_at, score_vector_json,
     critic_verdict_json, artifacts_ref, event_log_ref, neo4j_context_snapshot_ref)
claims(id, hypothesis_id, run_id, statement, source_artifact_ref,
       confidence, neo4j_claim_id, embedding)
approvals(...)
budgets(...)
events(...)

Neo4j stores graph-native node labels like Paper, Method, Claim, Entity, and HypothesisSeed, connected by relationships such as SUPPORTS, CONTRADICTS, and USES.

External integrations

Reasoning

  • Deep Agents CLI and LangSmith Deployments
  • REST + SSE runtime calls
  • Model routing across OpenAI, Anthropic, Google, and more

Execution + storage

  • Docker, Modal, Colab backends
  • MinIO or S3-compatible object store
  • Neo4j Community Edition + Postgres + Redis

Non-functional requirements

  • Performance: DAG queries under 100 ms for 10k-node trees; domain graph queries under 200 ms for 1M-node graphs.
  • Reliability: orchestrator crash recovery, replayable kept runs, graceful degradation if Neo4j is unavailable.
  • Security: secrets never enter agent prompts; dangerous actions require approvals; agent sandbox and GPU backend remain isolated.
  • Portability: local development comes up with Docker Compose; runtime and backend layers remain swappable.

Cost model

Crucible uses beam-bounded search plus context compaction to keep agent cost near the same order of magnitude as Karpathy-style loops while exploring a wider search surface.

ItemTarget

Status target: same cost class as linear autoresearch, but wider and better-instrumented.

Phased delivery

Phase 1

Replace Codex with Deep Agents, keep Postgres DAG, ship LocalBackend, basic MCP server, evaluator, CLI, and nanochat example.

Phase 2

Add Critic independence, Neo4j context engine, Modal backend, UI, trace panel, evidence graph, and richer scheduler scoring.

Phase 3

Add Colab backend, polished docs, comparison demo, contributor guide, and public launch readiness.

Out of scope

Domain packs, Kubernetes/SLURM orchestration, hosted SaaS, and active-learning research policies remain deferred.

Open questions

  • Should v2 ship a parallel fallback reasoning adapter in case Deep Agents beta surfaces change?
  • Should determinism mode be mandatory for replay-critical programs?
  • How aggressive should automatic confirmation runs be for quarantined hypotheses?
  • Should graph ingestion rely on spaCy + LLM assistance in v2, or a dedicated extraction model?
  • Is a 5k-node UI cap acceptable for v2 DAG rendering?
